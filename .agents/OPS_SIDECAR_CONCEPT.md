# Концепция: Ops Sidecar (Node Agent) & Управление проектами

**Дата создания:** 2026-10-02
**Статус:** Архитектурная инициатива (обсуждение, сбор требований владельца)
**Контекст:** Bot Chassis (`C:\Python\bot_chassis`), кузова (PsyBot, Listener, Profiling), серверная инфраструктура.

---

## 1. Терминология и происхождение

### 1.1 Что такое Sidecar (Сайдкар)
* **Происхождение:** от английского *sidecar* — «мотоциклетная коляска (люлька)».
* **Откуда пришёл:** паттерн микросервисной архитектуры из мира Docker и Kubernetes (K8s).
* **Смысл:** мотоцикл едет сам (это основной процесс бота), а в «люльке» рядом сидит вспомогательный процесс, который решает сервисные задачи (логирование, мониторинг, проксирование трафика, обновление). Мотоцикл может заглохнуть, но люлька никуда не денется.
* **Принцип:** Sidecar не вмешивается в бизнес-логику приложения, но делит с ним общую среду (сервер/диск) и заботится о его инфраструктурном здоровье.

### 1.2 Что такое Node Agent (Агент узла)
* **Происхождение:** классическая серверная инженерия и системное администрирование (SysAdmin / SRE).
* **Примеры в индустрии:** Datadog Agent, Zabbix Agent, New Relic, Telegraf, Prometheus Node Exporter.
* **Смысл:** легкий автономный процесс-демон, постоянно запущенный на сервере (ноде), который собирает телеметрию железа, проверяет жизнеспособность запущенных служб и выполняет команды управления хостом.

### 1.3 Как это называют в сообществе сисадминов и DevOps
* **«Супервизор» (Supervisor):** управляющий процесс, следящий за потомками (`supervisord`, `systemd`).
* **«Сторож» (Watchdog):** механизм отслеживания зависаний с перезапуском по тайм-ауту.
* **«Демон обслуживания» (Ops Daemon / Management Sidecar):** агент автоматизации рутины деплоя, бэкапов и логов.

## 2. Архитектурное разделение: Рама vs Кузов vs Ops Sidecar

```
┌─────────────────────────────────────────────────────────────┐
│                       СЕРВЕР (HOST)                         │
│                                                             │
│  ┌───────────────────────┐       ┌───────────────────────┐  │
│  │   Процессы Проектов   │       │   Независимый Контур  │  │
│  │                       │       │                       │  │
│  │ ┌───────────────────┐ │       │ ┌───────────────────┐ │  │
│  │ │      PsyBot       │ │       │ │    Ops Sidecar    │ │  │
│  │ │ (Кузов + Рама v1) │ │       │ │   (Node Agent)    │ │  │
│  │ └───────────────────┘ │       │ └─────────┬─────────┘ │  │
│  │ ┌───────────────────┐ │       │           │           │  │
│  │ │   Chat Listener   │ │       │           ▼           │  │
│  │ │ (Кузов + Рама v1) │ │       │ ┌───────────────────┐ │  │
│  │ └───────────────────┘ │       │ │ Master Ops Bot    │ │  │
│  │ ┌───────────────────┐ │       │ │ (Telegram админка │ │  │
│  │ │  Любой сторонний  │ │       │ │  только владельца)│ │  │
│  │ │ проект (без рамы) │ │       │ └───────────────────┘ │  │
│  │ └───────────────────┘ │                               │  │
│  └───────────────────────┘                               │  │
└─────────────────────────────────────────────────────────────┘
```

1. **Рама (`bot_chassis`):** Python-библиотека. Живёт **внутри** процесса кузова. Даёт нижнее меню, поддержку, админку пользователей, Stars, локальный SQLite.
2. **Кузов (PsyBot, Listener, Profiling):** продуктовый код бота с клиническими шкалами, обработчиками чатов или аналитикой.
3. **Ops Sidecar / Node Agent:** **внешний независимый процесс**. Он не зависит от кода ботов. Если бот упал с критической ошибкой, Sidecar остаётся жив и позволяет владельцу удалённо реанимировать сервис.

## 3. Мастер-бот владельца (Master Ops Bot)

Вместо того чтобы вшивать опасные системные права в публичных ботов (где есть риск взлома или утечки админки), создаётся **один выделенный закрытый бот управления**:

* Доступ **строго по белому списку `telegram_id` владельца** (все остальные запросы игнорируются наглухо).
* Единая диспетчерская вышка для всех проектов сервера.

### Функции Мастер-бота:
1. **Сводная панель статусов (Fleet Dashboard):**
   * Список всех процессов: `🟢 psybot@bpd`, `🟢 psybot@adhd`, `🔴 chat_listener`, `🟢 profiling`.
   * Время аптайма каждого процесса.
2. **Удалённый запуск упавших ботов:**
   * Если бот упал и не стартует сам, кнопка `[ 🚀 Запустить ]` поднимает его через системный менеджер.
3. **Удалённый сборщик логов (Log Tail):**
   * Кнопка `[ 📄 Лог (50 строк) ]` по любому выбранному боту.
   * Читает системный журнал (`journalctl -u <unit> -n 50 --no-pager`) и присылает выжимку прямо в чат Telegram. Больше не нужно открывать терминал и вводить SSH.
4. **Перехват OOM Killer (Out-Of-Memory Killer):**
   * **Что это:** когда бот или скрипт съедает всю доступную оперативную память сервера, ядро Linux без предупреждения убивает процесс сигналом `SIGKILL` (код 137). Бот умирает мгновенно и физически не успевает отправить алерт в свой чат ошибок.
   * **Как ловит Sidecar:** агент отслеживает события ядра через системный журнал (`dmesg` / `journalctl`). При обнаружении OOM-события мгновенно отправляет владельцу:
     *«🚨 Бот psybot@bpd был убит ядром Linux из-за нехватки памяти (OOM Killer)! Потребление перед смертью: 1.8 GB. Рекомендуется рестарт с оптимизацией»*.
5. **Мониторинг железа и ресурсов (System Telemetry):**
   * Память: сколько потребляет каждый бот отдельно и сколько свободно на сервере.
   * Диск: свободное место в GB и %. Раннее предупреждение при падении ниже 15% (критично для SQLite WAL!).
   * CPU: нагрузка процессора.

## 4. Движок безопасного обновления и отката (Safe Update & Rollback Engine)

### 4.1 Архитектура Two-Service (Двухсервисный паттерн)
* Обновлением занимается не сам бот, а One-Shot сервис Sidecar.
* Бот через `ProcessControlPort` лишь инициирует задачу: `systemctl start ops-updater@bot_chassis.service`.

### 4.2 Алгоритм работы со сторожевым таймером (Watchdog)
1. **Пре-чек:** создание снапшота рабочей SQLite-базы перед апдейтом.
2. **Фиксация версии:** запись текущего стабильного хеша/версии (`PREV_VERSION=0.3.0`).
3. **Установка:** `pip install bot-chassis==0.3.1` (или `git pull`).
4. **Рестарт:** перезапуск целевой группы ботов.
5. **Сторожевой таймер (30 сек):**
   * Sidecar ожидает подтверждения здоровья от ботов (проверка процесса `is-active` + опрос внутреннего readiness-флага).
6. **Развилка:**
   * **Успех:** все боты подтвердили готовность → фиксация новой версии, уведомление владельцу:
     *«✅ Обновление до 0.3.1 успешно завершено. Все 7 процессов в строю»*.
   * **Сбой (бот упал, ImportError, синтаксическая ошибка, зависание):** таймер 30 сек истёк, бот мёртв → **автоматический аварийный откат**:
     1. Вызов `pip install bot-chassis==0.3.0`.
     2. Восстановление снапшота базы (если миграция сломала таблицы).
     3. Повторный запуск старой версии.
     4. Алерт владельцу: *«❌ Обновление до 0.3.1 провалено! Сработал аварийный откат на 0.3.0. Сервис восстановлен. Лог сбоя прикреплён»*.

### 4.3 Журнал версий `releases.yaml` (App Store Style)
Машиночитаемый манифест в корне репозитория рамы (и в проектах):

```yaml
0.3.1:
  date: "2026-10-01"
  title: "UI, навигация и поддержка"
  highlights:
    - "Подписи кнопок: Аккаунт / Инфо / Поддержка"
    - "Отмена на стартовом экране, Назад во вложенных"
    - "Синее меню: /start вверху, /menu внизу"
    - "Ответ оператора одним сообщением"
  breaking_changes:
    wiring: "build_support_prompt_keyboard (cancel_* -> back_*)"
  compatibility:
    psybot: "🟡 Требуется удаление дубля языка"
    listener: "🟢 Полная совместимость"
    profiling: "🔴 Hold (зафиксирован на 0.2.1)"
```

* Мастер-бот читает этот файл и перед обновлением выводит владельцу понятную карточку с предупреждением о состоянии «проводов» каждого кузова.

## 5. Независимые бэкапы через Sidecar

* Вынос генерации и ротации бэкапов из процесса бота в Ops Sidecar.
* Бот не тратит CPU и память на сжатие zip и экспорт.
* Sidecar делает снимок по ночному расписанию (04:00 UTC+5), проверяет `PRAGMA integrity_check`, упаковывает и ротирует 14 daily / 8 weekly.
* Возможность отправки зашифрованного архива в облачное хранилище S3 или резервный канал.

## 6. Что если сам Ops Sidecar упадёт?

Вопрос владельца: *«А если этот скрипт сам упадёт? Нужен ли ему постоянный процесс?»*

**Решение на уровне операционной системы (Systemd PID 1):**
* В Linux самым главным «надсмотрщиком» является ядро и `systemd` (PID 1). Его невозможно «уронить» обычным падением скрипта.
* В unit-файле Ops Sidecar настраивается директива:
  ```ini
  [Service]
  Restart=always
  RestartSec=5s
  ```
* Если Sidecar по какой-то причине завершится с ошибкой, сам `systemd` перезапустит его через 5 секунд.
* Для лёгких задач (бэкапы, ротация, health-check) могут использоваться независимые `systemd timers` или классический `cron`, которым вообще не нужен постоянно работающий в фоне демон.

## 7. Готовность к коммерциализации (Chassis as a Product)

Владелец отметил важный вектор: в будущем рама и Ops-контур могут стать готовой платформой для продажи и подключения сторонних Telegram-проектов.

Для этого архитектура изначально проектируется модульной:
1. **Чёткие паспорта интеграции кузовов:** сторонний разработчик читает спецификацию и подключает свой проект за 15 минут.
2. **Изолированный Ops Sidecar:** ставится на сервер клиента как готовый инструмент администрирования.
3. **Стандартизированные контракты проводов (Ports & Middleware):** никаких жестких зависимостей от конкретного домена.

## 8. Ограничения безопасности

Ops Sidecar получает системные права, поэтому его нельзя собирать как обычную
админку бота. Для будущей спецификации обязательны следующие границы:

1. Команды работают только по allowlist проектов и systemd units. Имена unit,
   пути и аргументы нельзя принимать из Telegram как произвольный текст.
2. Telegram ID владельца проверяется до разбора команды. Токен Master Ops Bot
   хранится вне репозитория, а опасные действия требуют короткоживущего
   подтверждения.
3. Sidecar запускается от отдельного системного пользователя. `sudoers`
   разрешает только заранее перечисленные операции. Shell-команды из входных
   данных запрещены.
4. Перед отправкой логов в Telegram применяется маскирование токенов, DSN,
   персональных данных и платёжных идентификаторов. Объём ответа ограничен.
5. Обновление использует отдельный release-каталог или virtualenv и атомарное
   переключение версии. `git pull` и `pip install` поверх живого окружения не
   входят в безопасный сценарий.
6. Миграции БД должны быть обратно совместимыми. Автоматическое восстановление
   старого снимка допустимо только в maintenance-окне, когда после снимка не
   было новых записей. Иначе откат кода не должен откатывать пользовательские
   данные.
7. Тайм-аут готовности задаётся для каждого сервиса. Фиксированные 30 секунд
   остаются примером, а не контрактом.
8. Бэкап считается рабочим после регулярной проверки восстановления. Ключ
   шифрования хранится отдельно от архивов.

## 9. Порядок реализации

Эта инициатива не входит в релиз `0.3.1`. Следующий пакет начинается с
отдельной спецификации и threat model (модели угроз). Затем можно делать
read-only прототип: статус процессов, память, диск и безопасный хвост логов.
Рестарты, обновления и автоматический откат открываются только после аудита
прототипа и проверки на тестовом сервере.
