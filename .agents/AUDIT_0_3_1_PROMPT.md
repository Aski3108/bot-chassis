### 2.2. Канон навигации

1. Корень Поддержки: нижняя кнопка ровно `Отмена`, `callback_data` —
   `core_nav:cancel`. Клик приводит к вызову `render_start_callback`
   ровно один раз и **не** шлёт Reply Keyboard.
   Повтори без `render_start_callback` и с выключенным переключателем языка:
   штатная стартовая карточка всё равно обязана прийти, без Reply Keyboard.
   Повтори с **`render_start_callback`**, вернувшим `None`: внутри фабрики
   должен сработать штатный fallback карточки, а не тишина.
   Не смешивай два callback: фабричный `on_support_back` после успешной
   доставки штатно возвращает `None`, и это **не** повод слать второй fallback.
   Fallback роутера разрешён только при полном отсутствии `on_support_back`;
   внутренний fallback `render_start_callback` проверяется внутри фабрики.
   `/start` по-прежнему шлёт носитель с клавиатурой, затем карточку. Смешивать
   эти два потока — находка.
2. Форма тикета, форма отзыва, экран доната: нижняя кнопка ровно `Назад`,
   ведёт в корень Поддержки. Кнопки закрытия всего окна там нет.
3. Корневые экраны Аккаунта и Info, собранные из `ChassisScreen`, получают ряд
   `Отмена` последним, ниже языкового ряда.
4. `append_cancel_row`, применённый дважды, не создаёт двух кнопок «Отмена».
   Прогони руками также ряд, где рядом с прежней отменой есть полезная кнопка:
   соседняя кнопка не должна исчезнуть. `append_back_row` дважды даёт ровно
   один последний ряд `Назад`.
5. **Проверка на оставленные старые ветки.** В `src/` должен быть **ровно
   один** обработчик на действие:
   - `rg "core_sup:back|CB_SUPPORT_BACK" src/` — только объявление константы и
     упоминание в фильтре общего хэндлера;
   - `rg "core_sup:cancel|CB_SUPPORT_CANCEL" src/` — то же;
   - отдельных функций `handle_support_back` и `handle_support_cancel` быть не
     должно.
   Два обработчика одного действия — БЛОКЕР.
   Отдельно нажми старый `core_nav:close`: он только закрывает карточку и не
   вызывает стартовый renderer. Изменение старого смысла — БЛОКЕР
   совместимости.
6. **Проверка на мёртвые параметры.** `build_support_prompt_keyboard` не
   должна содержать параметров, которые никто не читает. Если `cancel_callback`
   или `cancel_label` остались в сигнатуре — находка СРЕДНЯЯ с указанием, что
   это ровно та «заплатка», которую пакет должен был убрать.
7. `rg "← Назад"` по `src/` — стрелочных подписей остаться не должно, канон
   требует строго `Назад` и `Отмена`.
8. Корневой callback, вернувший уже отправленный `Message`, всё равно получает
   каноническую `Отмена`; одного warning в логах недостаточно. Аннотации обоих
   renderer callback допускают `Message | ChassisScreen | None`.
9. Форма отзыва и каталог донатов имеют последний ряд `Назад` в корень
   Поддержки. Для кузовных FAQ/платёжных подэкранов публично экспортирован
   единый `append_back_row`. Второй навигационный стек не создан.
   Helper идемпотентен по `callback_data`: два применения с одинаковым callback
   не создают дубль. `build_support_prompt_keyboard` и
   `build_donation_keyboard` сразу строят окончательный нижний ряд и не требуют

### 2.4. Карточка тикета и «От:»

1. Прогони живой сценарий на временной SQLite: создать тикет от пользователя с
   username, закрыть, открыть снова. После каждого перехода в тексте карточки
   есть `От:`, имя и `@username`.
2. Повтори для пользователя **без** username — должно быть `нет username`, и
   формулировка должна совпадать с той, что уже используется в шапке нового
   обращения. Вторая формулировка того же смысла — находка.
3. Пустая строка перед `<b>Статус:</b>` присутствует.
4. **Миграция.** Собери БД по схеме `0.3.0` (без `user_full_name` /
   `user_username`), положи в неё строку тикета, прогони инициализацию
   хранилища. Проверь: столбцы добавились, старая строка цела,
   `get_ticket` возвращает `None` в новых полях и не падает, карточка
   старого тикета рисуется без `От:` и без исключения.
5. `username` хранится без ведущего `@`, нормализация сделана в одном месте.
   Два места нормализации — находка.
   Для `full_name="A & B <C>"` проверь SQLite напрямую: там обязана лежать
   сырая строка с `&` и `<`, а не `&amp;` / `&lt;`. Новая карточка и карточка
   после смены статуса экранируют её ровно один раз.
6. В SQLite не появилось текстов сообщений, эмодзи или кириллицы в кодах
   состояний. Проверь `PRAGMA table_info(support_threads)` и схему.
7. Передай старый пользовательский `thread_store`, у которого `register` не
   принимает `full_name` / `username`: тикет должен зарегистрироваться ровно
   один раз. Затем заставь внутренность `register` выбросить `TypeError`:
   ошибка не должна маскироваться повторным вызовом. Fallback через
   `except TypeError` вокруг **вызова** `register` — находка. Исключения
   самого `inspect.signature` ловить можно; это не вызов store.

   сломалась в новом режиме — БЛОКЕР.

7. Проверка темы (`WRONG_THREAD`) и проверка origin (`FOREIGN_ORIGIN`) не

8. Текст и caption с обычными символами `<`, `>` и `&` успешно доставляются с

   а не сырые поля. Telegram entities не потеряны.
9. Ответ, который после добавления шапки превышает 4096 символов текста или
   1024 символа caption, не обрезается и не падает: применяется прежний

5. Карточка тикета при показе истории не редактируется.
6. Пустой тикет даёт `История пуста` без исключения.
7. `callback_data` кнопки укладывается в 64 байта вместе с UUID тикета.
   Посчитай длину.
8. В БД не появилось текстов сообщений.
9. На один реальный ход диалога приходится ровно одна строка истории. Исходник
