# Bot Chassis 0.3 — подробный план Operational Upgrade

**Статус:** план принят владельцем 2026-09-28. Gate 0 — документационный
коммит control plane. Код гейтов 1–13 не начат.
**Базовая версия:** `0.2.2`, родитель Gate 0 — `42c3cce`, исходный сьют: `110 passed`.
**Целевая версия:** `0.3.0`.
**Готовность:** после Gate 0 обязателен независимый аудит B0. Gate 1 начинается
только после `PASS` или принятого владельцем `PASS WITH NOTES`.
**Главное правило:** рама предоставляет универсальные механизмы. Названия
конкретных ботов, `/detect`, опросники, анализы и другие сценарии кузова сюда
не входят.

---

## 1. Что именно строим

`0.3.0` — эксплуатационное обновление общей рамы:

1. Компактное единое нижнее меню и чистое системное меню Telegram.
2. Новая кнопочная админка с переходящими экранами и разделением прав.
3. Маршрутизация поддержки, аудита, событий и ошибок по темам Telegram.
4. Жизненный цикл пользователя отдельно для каждого фактического бота сети.
5. Настоящая Excel-книга для просмотра всей базы данных.
6. Ручные и автоматические резервные копии SQLite.
7. Универсальное управление перезапуском одного процесса или всей сети.
8. Вечерние отчёты только по данным рамы.
9. Чистый канон переменных окружения.
10. Финальное переименование GitHub-репозитория и рабочей папки без смены
    Python-импорта `bot_chassis`.

## 2. Что остаётся в кузовах

В раму не переносить:

- `/detect`, ввод ссылки на канал, TXT и произвольного текста;
- экран ожидания и отмены анализа;
- прогресс анализа и рендер итоговой картинки;
- опросники, клинические шкалы, доменные задачи и их статистику;
- конкретные имена процессов вроде BPD, ADHD или Profiling;
- правила развёртывания конкретного проекта.

Рама только принимает от кузова:

- дополнительные команды системного меню, например `/detect`;
- список доступных целей перезапуска через универсальный порт;
- исполнитель перезапуска, настроенный конкретным проектом;
- доменные кнопки и обработчики через существующие точки подключения.

Сценарий `/detect`, описанный владельцем, передать в backlog Profiling
Framework из отдельного чата/корня этого проекта. Из корня Bot Chassis
соседние репозитории не открывать и не менять.

Отдельный живой blocker PsyBot, не задача рамы: при `/start` SQLAlchemy получил
`sqlite3.OperationalError: no such table: assessment_answers`. Таблица
`assessment_answers` относится к доменной базе опросников PsyBot. Проверить в
его репозитории применение миграций и фактический путь к базе; общий обработчик
ошибок шасси только показал пользовательскую заглушку.

## 3. Зафиксированные продуктовые решения

### 3.1 Нижнее меню

- Все включённые служебные кнопки всегда находятся в одном ряду.
- Базовая фиксированная тройка:
  `[👤 Личный кабинет] [ℹ️ Info/FAQ] [💬 Поддержка]`.
- Если раздел когда-нибудь отключён, оставшиеся служебные кнопки не разбивать
  на отдельные строки.
- Доменные ряды кузова по-прежнему располагаются выше служебного ряда.
- Английская подпись остаётся компактной: `ℹ️ Info/FAQ`.

### 3.2 Системное меню Telegram

- Встроенная команда рамы: `/menu` — `📱 Восстановить кнопки меню`.
- `/start`, `/help`, `/support` остаются рабочими скрытыми командами для
  старых ссылок и совместимости, но не показываются в системном списке.
- Кузов может явно добавить свои команды, например `/detect`.
- Если кузов ничего не передал, в списке видна только `/menu`.
- Обновление этого поведения — разрешённое изменение ранее замороженного
  кнопочного контракта для релиза `0.3.0`.

`/start` не обязан отображаться в системном списке, но всегда остаётся рабочим
аварийным входом. Он сбрасывает ожидания и активную пользовательскую сессию,
восстанавливает клавиатуру и заново открывает стартовый экран кузова через
явный callback. Кузов не должен параллельно регистрировать второй независимый
`/start`, иначе возможны двойные ответы и разные состояния.

### 3.2.1 Мгновенный переключатель языка

- В интерфейсе одна кнопка-переключатель, без промежуточного выбора RU/EN.
- Один клик меняет `ru ↔ en`.
- На русском экране подпись: `🌐 English / Русский`.
- На английском экране подпись меняет порядок: `🌐 Русский / English`.
- Кнопка находится на первоначальном экране `/start` и внутри Info. В саму
  карточку каждого вопроса её дублировать не нужно, но нижнее меню остаётся
  доступным: пользователь может открыть Info и сменить язык даже во время
  активного опросника.
- После клика одновременно обновляются:
  - сохранённая локаль пользователя;
  - постоянная нижняя клавиатура рамы;
  - текущая карточка рамы;
  - текущий экран кузова через переданный кузовом callback перерисовки.
- Рама предоставляет сам переключатель и хранение локали, но не знает тексты
  опросника. Кузов обязан уметь заново отрисовать свой текущий экран на новой
  локали.
- Смена языка не отменяет опросник, не очищает ответы и не сбрасывает номер
  вопроса. После возврата из Info продолжается тот же шаг уже на новом языке;
  если кузов поддерживает немедленную перерисовку, он может сразу обновить
  текущую доменную карточку через `on_locale_changed`.
- Первый язык определяется только при первом контакте по Telegram
  `language_code`. Bot API передаёт язык интерфейса Telegram, но не страну,
  гражданство, SIM-регион или фактическое местоположение пользователя.
- Согласованная стартовая RU-группа кодов:
  `ru`, `be`, `uk`, `kk`, `ky`, `uz`, `tg`, `tk`, `hy`, `az`, `ka`, `pl`.
  Региональные варианты сначала приводятся к базовому коду: например,
  `ru-RU → ru`, `uk-UA → uk`, `pl-PL → pl`.
- Любой другой известный код и отсутствие `language_code` запускают английский
  интерфейс. Поэтому Канада с `en`/`fr` и большинство Европы стартуют на EN,
  а польский код `pl` — на RU по отдельному решению владельца.
- Список RU-группы должен быть настраиваемой политикой рамы, а не разбросанным
  по обработчикам условием. Это позволит кузову расширить его без переписывания
  механизма локализации.
- Точно определить «российский аккаунт» или страну СНГ по Bot API невозможно:
  если человек в России использует Telegram на английском, первичный экран
  будет EN; если человек в Канаде использует русский — RU. Кнопка на `/start`
  позволяет сразу исправить выбор одним нажатием.
- После первого ручного переключения сохранённый выбор всегда важнее
  `language_code` и больше автоматически не перезаписывается.
- Текущую пару кнопок «Русский / English» удалить. Она понадобится только при
  появлении третьего языка и нового отдельного решения владельца.

### 3.2.2 Контракт единого `/start` и миграция кузовов

- Рама остаётся единственным владельцем `Command("start")`. Кузов снимает свой
  обработчик `/start` и передаёт `render_start_callback` в фабрику.
- Порядок запуска фиксирован: очистить только пользовательские ожидания рамы →
  закрыть предыдущую карточку рамы → определить/загрузить локаль → отправить
  носитель постоянной Reply-клавиатуры → вызвать `render_start_callback` ровно
  один раз для стартовой inline-карточки кузова.
- `welcome_text` не создаёт третье приветственное сообщение. В `0.3` это текст
  носителя Reply-клавиатуры; если кузову отдельный носитель не нужен, он
  передаёт `None`, а рама использует короткое нейтральное «Главное меню».
- Старый кузов со своим более ранним `Command("start")` считается не
  мигрированным: в каноне дать явный чек-лист удаления обработчика и тест,
  который обнаруживает двойной ответ.
- `render_start_callback` и callback возврата из поддержки — одна и та же
  точка входа, чтобы «Назад» и `/start` строили одинаковый стартовый экран.
- Фабрика сохраняет старое поведение, если callback не передан: показывает
  только `welcome_text`/нейтральный текст с постоянной клавиатурой.

### 3.3 Права админки

Обычный администратор видит:

- краткую сводку;
- отдельный экран статистики;
- поиск пользователя;
- карточку пользователя и разрешённые санкции;
- рубильник сервисного режима.

Только суперадминистратор видит:

- рассылку;
- Excel-выгрузку;
- ручной бэкап `.db`;
- управление ролями и подарками;
- перезапуск одного процесса;
- перезапуск всей зарегистрированной сети.

### 3.4 Экранная модель админки

- Переходы внутри раздела редактируют текущую панель на месте.
- Есть явные кнопки «Назад» и «В главное меню».
- Завершённое значимое действие создаёт отдельный постоянный текстовый отчёт
  без активных кнопок.
- Старая активная панель удаляется или лишается кнопок.
- Новая главная панель отправляется последним сообщением вниз чата.
- Предпросмотры и подтверждения после использования теряют кнопки, чтобы
  действие нельзя было случайно повторить.
- В памяти хранится ID активной панели каждого администратора. Потеря этого
  ID после рестарта безопасна: команда `/admin` создаёт новую панель.

### 3.5 Служебные направления Telegram

Конфиг рамы получает необязательные поля:

- `support_chat_id` + `support_thread_id` — обращения пользователей;
- `audit_chat_id` + `audit_thread_id` — действия администраторов и оплаты;
- `audit_chat_id` + `ops_thread_id` — ошибки, рестарты и результат бэкапа;
- `audit_chat_id` + `events_thread_id` — новые пользователи, изменение
  Telegram-статусов и периодические отчёты.

Если `*_thread_id` равен `None`, сообщение идёт в общий чат. Старые вызовы без
новых параметров работают как в `0.2.2`.

Каноническое имя служебного чата остаётся `AUDIT_CHAT_ID`. В документации
кратко пояснить: это закрытый служебный чат суперадминистраторов для аудита и
системных уведомлений. `SUPERADMIN_CHAT_ID` не вводить.

### 3.6 Статусы пользователей

Санкции остаются общими для tenant-сети:

- `is_banned` — обычный бан всей сети;
- `is_shadow_banned` — теневой бан всей сети.

Telegram-жизненный цикл хранится отдельно для каждого фактического бота:

- `active` — пользователь доступен в этом боте;
- `stopped` — пользователь остановил/заблокировал этого бота;
- `deleted` — Telegram сообщил об удалённом аккаунте;
- отсутствие ряда — `unknown`, старый пользователь ещё не наблюдался этим
  фактическим ботом после обновления.

Любое новое входящее событие от пользователя переводит статус текущего бота
в `active`. Временные сетевые и серверные ошибки статус не меняют.

В карточке `/user` сначала показывается общая санкция, затем таблица ботов:

```text
Санкции сети: нет
BPD:       активен
ADHD:      остановлен пользователем
Profiling: неизвестно
```

Названия BPD/ADHD не хранятся в коде рамы. Кузов передаёт отображаемые имена,
а база хранит `origin_bot_id` и фактический числовой Telegram bot ID.

### 3.7 Поддержка как продолжаемый диалог

Кнопка нижнего меню «Поддержка» сначала открывает обзорный экран, а не режим
ввода и не список сумм:

1. `📝 Запрос в поддержку`;
2. `⭐ Оставить отзыв`;
3. `💛 Поддержать проект`;
4. `← Назад`.

`Запрос в поддержку` открывает отдельную карточку с короткой инструкцией:
можно отправить текст, изображение, видео, голосовое сообщение или документ.
На карточке есть `Отмена` и `Назад`; ожидание сообщения включается только на
этом экране.

`Поддержать проект` открывает следующий экран с донатными SKU. Рама не
зашивает суммы: она отображает переданные кузовом `SkuItem` с
`issues_voucher=False` либо отдельный `DonationCatalogPort`. Для первого
PsyBot-конфига согласован набор 50/100/500 Stars, но это настройка потребителя,
а не универсальный контракт. Для `0.3.0` поддерживаются только официальные
Telegram Stars; сторонние рублёвые платёжные шлюзы в раму не добавляются.
Фабрика больше не вставляет донатные SKU прямо в форму запроса.

Рублёвый эквивалент — только необязательная настраиваемая подсказка, а не
зашитый курс: стоимость Stars меняется по стране и площадке покупки.

`Оставить отзыв` — универсальная точка подключения:

- рама показывает короткую форму и принимает текст/медиа;
- поддерживается текст, одно медиа, либо медиа с подписью;
- назначение задаётся внешним `review_sink` (куда передать отзыв);
- если `review_sink` не подключён, кнопка скрывается без заглушки «Скоро»;
- перед возможной публичной публикацией пользователь явно соглашается на неё;
- по умолчанию отзыв сначала уходит в закрытую очередь модерации, где
  суперадминистратор выбирает «Опубликовать» или «Отклонить»;
- публичный канал-портфолио, его тема и рекламный текст являются настройкой
  проекта, а не захардкоженной частью рамы.
- после одобрения и публикации пользователь получает прямую ссылку на
  опубликованный пост в канале;
- адрес канала и публичная ссылка задаются через безопасные настройки
  (`REVIEWS_CHANNEL_ID`, `REVIEWS_CHANNEL_URL`) и отражаются в `.env.example`;
  настоящий токен или секрет в пример не помещается.

`Назад` вызывает переданный кузовом рендер стартового экрана. Рама не знает,
что на конкретном стартовом экране находятся 18+, дисклеймер или вопросы.
Она только предоставляет безопасный callback возврата.

Тикет имеет статусы:

- `open` — новое обращение;
- `in_progress` — оператор ответил, диалог продолжается;
- `closed` — оператор явно завершил обращение.

Первый ответ не закрывает тикет. Оператор может ответить несколько раз.
Пользователь получает кнопку «Ответить поддержке», и следующее сообщение
возвращается в тот же тикет. Закрытие выполняется отдельной кнопкой
`✅ Закрыть обращение`; предусмотреть `↩️ Открыть снова`.

В теме Telegram видна фактическая переписка. В SQLite сохраняются только
маршрутизация, направления сообщений, Telegram message ID, даты и статусы.
Содержимое личной переписки в базу шасси не копировать.

Ответ оператора принимается только как Reply на зарегистрированное сообщение
в исходном чате и исходной теме. После закрытия карточка получает отметку
`✅ Обращение обслужено`.

### 3.7.1 Одно сообщение на один пользовательский клик

- Нажатие Info создаёт или обновляет ровно одну карточку.
- Нажатие Language выполняет ровно одно переключение и одну перерисовку.
- Нажатие `/start` создаёт один клавиатурный носитель и один стартовый экран
  кузова, если кузову нужны оба сообщения.
- Двойная регистрация одинакового обработчика рамой и кузовом запрещена и
  проверяется интеграционным тестом.

### 3.7.2 Личный кабинет и коммерческие слоты

Универсальные разделы кабинета остаются разделёнными:

- профиль;
- доступ;
- единицы разовых услуг;
- доменные результаты/тесты через слот кузова.

Слово «талоны» не зашивать в новый UI. Пользовательская подпись становится
настраиваемой; рабочий вариант — «Токены». Если платёжный контур выключен,
этот слот полностью скрывается. То, сколько расширенных отчётов даёт один
токен, определяет кузов, а не рама.

Внутренний `slot_id="vouchers"` в `0.3` не переименовывать: меняется только
видимая подпись. Иначе без пользы ломаются существующие порты, тесты и кузова.

### 3.8 Excel и бэкап — разные функции

Excel:

- человекочитаемая книга `.xlsx`;
- один лист на каждую таблицу SQLite;
- все существующие поля таблиц сохраняются;
- лист пользователей дополнительно получает понятный итоговый статус и
  кликабельный профиль;
- `https://t.me/<username>` при наличии username;
- `tg://user?id=<id>` при отсутствии username;
- доступ только суперадминистратору в личном чате.

Бэкап:

- настоящий SQLite-снимок, пригодный для восстановления;
- ручная кнопка отдаёт `.db`;
- автоматическое хранение использует сжатый архив с `.db` внутри;
- копируется только база данных шасси, не файлы кузова;
- создание через уже безопасный `sqlite3.Connection.backup()`.

### 3.9 Расписание

- Автоматический бэкап: ежедневно в `04:00`, часовой пояс `UTC+5`.
- Вечерний отчёт: ежедневно в `23:30`, `UTC+5`, за период после предыдущего
  успешного отчёта.
- В воскресный вечер ежедневный отчёт дополняется недельным итогом.
- В последний календарный день месяца он дополняется месячным итогом.
- Отдельные утренние отчёты не создаются.

Отчёты содержат только показатели рамы:

- новые пользователи и первые запуски по фактическим ботам;
- active/stopped/deleted/unknown;
- общие баны и теневые баны;
- платежи Stars;
- созданные, активные и закрытые тикеты;
- ошибки, рестарты и результат резервного копирования.

Число анализов, тестов, файлов, лидов и другие метрики кузова сюда не входят.

### 3.9.1 Текст необработанной ошибки

Пользовательский текст без тревожного эмодзи и без восклицания:

```text
Произошла непредвиденная ошибка.
Мы уже занимаемся этим вопросом.
```

Полный traceback отправляется только в ops-тему. Пользователю технические
детали и внутренние имена не показываются.

### 3.10 Ротация резервных копий

Принята компактная схема:

- 14 последних ежедневных снимков;
- 8 еженедельных снимков;
- месячные снимки пока не хранить.

Еженедельный снимок не создаётся второй полной копией в тот же день: выбранный
дневной архив переносится в недельную категорию. Максимум — 22 архива. При
создании нового лишний самый старый архив соответствующей категории удаляется.

Алгоритм фиксирован:

- границы суток и календаря считаются в `UTC+5`;
- имя содержит фактический момент снимка и категорию:
  `daily_YYYY-MM-DD_HH-mm-ss_UTC+5.zip`;
- после успешной проверки воскресный daily-файл атомарно переименовывается в
  `weekly_...zip`, а не копируется;
- затем независимо оставляются 14 самых новых `daily_*` и 8 самых новых
  `weekly_*`; воскресенье, совпавшее с концом месяца, остаётся одной weekly-
  копией, потому что месячной категории в `0.3` нет;
- чистка выполняется после появления и проверки нового архива; при ошибке
  снимка существующие архивы не удаляются.

### 3.11 Первый запуск

Первый подтверждённый запуск пользователя в каждом фактическом боте сразу
создаёт событие в `events_thread_id`:

```text
Новый пользователь
@username · ID 123
Бот: <имя, переданное кузовом>
Источник: ref_456 или —
```

Повторный `/start` того же пользователя в том же боте новым запуском не
считается.

В событии первого запуска дополнительно показывается автоматически выбранная
локаль (`ru`/`en`) и исходный Telegram `language_code` для диагностики.

### 3.12 Принятые отмены и уточнения старого `TASK_TODO`

Этот план сознательно заменяет следующие старые формулировки очереди:

- `SUPERADMIN_CHAT_ID` не вводится; каноническим остаётся `AUDIT_CHAT_ID`, а
  назначение чата подробно документируется;
- подпись `ℹ️ Info / FAQ ❓` заменена на более компактную `ℹ️ Info/FAQ`;
- описание `/menu` становится `📱 Восстановить кнопки меню`, а не
  `📱 Открыть кнопки`;
- username хранится без `@`; ввод и показ поддерживают оба вида;
- FIFO за 60 дней заменён компактной ротацией 14 daily + 8 weekly;
- несуществующая команда `/unshadowban` не добавляется: действующий контракт
  `/shadowban <ID|username> 0|1` сохраняется. Отдельную человекочитаемую кнопку
  снятия теневого бана даёт админское досье;
- суммы 50/100/500 Stars относятся к конфигурации PsyBot, а не зашиваются в
  универсальную раму.

После утверждения `0.3` эти пункты нужно синхронизировать в `TASK_TODO`, чтобы
живая очередь и подробный план больше не противоречили друг другу.

## 4. Целевая модель данных

### 4.1 Новая таблица `user_bot_statuses`

Минимальные поля:

```sql
bot_id                    TEXT    -- общий tenant
user_id                   INTEGER
origin_bot_id             TEXT    -- логическое имя процесса
telegram_bot_id           INTEGER -- фактический бот из токена
status                    TEXT    -- active | stopped | deleted
first_seen_at             TEXT
last_seen_at              TEXT
status_changed_at         TEXT
last_error_code           TEXT NULL
```

Ключ: `(bot_id, user_id, telegram_bot_id)`.

Ограничение `CHECK` разрешает только `active`, `stopped`, `deleted`. Состояние
`unknown` в базу не пишется: это отсутствие ряда.

### 4.2 Расширение поддержки

В `support_threads` добавить без разрушения старых данных:

- `message_thread_id INTEGER`;
- `operator_id INTEGER`;
- `first_answered_at TEXT`;
- `closed_at TEXT`;
- `updated_at TEXT` используется для всех переходов состояния.

Статусы: `open → in_progress → closed`; `closed → in_progress` при явном
повторном открытии. Старый `answered` мигрируется в `closed` и больше не
создаётся новым кодом. Статус обновляется у всех строк одного `ticket_id`.

Добавить таблицу метаданных сообщений `support_ticket_messages`:

```sql
bot_id, ticket_id, direction, telegram_chat_id,
telegram_message_id, message_thread_id, created_at
```

`direction`: `user_to_support` или `support_to_user`. Текст сообщения не
хранить.

Лимит пяти обращений считается по числу различных `ticket_id` в состояниях
`open` и `in_progress`. Он запрещает только открытие шестого нового тикета;
ответы внутри уже существующего тикета лимит не проверяют и не могут оборвать
диалог посередине.

Добавить `review_submissions` — очередь отзывов без копирования содержимого:

```sql
bot_id, review_id, user_id, origin_bot_id,
source_chat_id, source_message_id,
moderation_chat_id, moderation_message_id,
published_chat_id, published_message_id,
consent_to_publish, status, created_at, reviewed_at, published_at
```

`status`: `pending | published | rejected`. Текст и медиа остаются в Telegram;
SQLite хранит только маршрутизацию, согласие, состояние и ID сообщений.

### 4.3 Задания фонового планировщика

Для защиты общей базы от семи одновременных процессов добавить
`scheduled_job_runs`:

```sql
bot_id, job_key, scheduled_for, claimed_by,
started_at, completed_at, status, details
```

Каждый процесс может увидеть наступление времени, но через короткую транзакцию
SQLite право выполнения получает только один. Это исключает семь одинаковых
бэкапов и семь одинаковых отчётов.

Обязательный уникальный ключ: `(bot_id, job_key, scheduled_for)`. Claim
делается атомарным `INSERT ... ON CONFLICT DO NOTHING`; только вставивший строку
процесс выполняет работу. `scheduled_for` — нормализованная граница периода в
UTC, рассчитанная из политики `UTC+5`, а не текущее время конкретного процесса.

### 4.4 Локаль пользователя

В `users` добавить:

- `telegram_language_code TEXT NULL` — последний сырой код Telegram только для
  диагностики;
- `locale_source TEXT NOT NULL` — `auto | manual | legacy`.

Существующие строки получают `legacy`: их сохранённый язык считается
осознанным и не переопределяется. Новый пользователь вставляется с локалью,
вычисленной resolver-политикой, и `locale_source='auto'`. Первый ручной клик
ставит `manual`; дальнейшие upsert обновляют сырой Telegram-код, но никогда не
меняют выбранную локаль. При отсутствии кода новый пользователь получает EN.

### 4.5 Username

- В базе username хранить без `@`.
- Поиск регистронезависимый, `@` во вводе необязателен.
- При получении нового username освободить такое же устаревшее значение у
  другого пользователя этого tenant, затем записать актуальное.
- Если Telegram сообщил отсутствие username, очистить старое значение.
- На старой базе при нескольких совпадениях админке показать кандидатов с ID,
  а не выбирать первого молча.

### 4.6 Миграция существующей базы

- Только добавляющие и повторяемые миграции: повторный запуск безопасен.
- Существующие `users`, санкции, оплаты, роли и тикеты не переписывать.
- Старым пользователям не назначать `active` задним числом.
- Их состояние для конкретного бота становится `active` при первом новом
  событии после установки `0.3.0`.
- Для старых открытых тикетов сохранить `open`; старые `answered` считать
  `closed`, если продолжение диалога невозможно восстановить.
- Все новые индексы и `CHECK` создаются повторяемо; миграция отдельно проверяет
  базу, где часть колонок уже появилась после прерванного запуска.

## 5. Новые универсальные интерфейсы рамы

### 5.1 `ProcessControlPort`

Рама не знает `systemd`, Docker и имена проектов. Она ожидает объект с
операциями:

- `list_targets()` — доступные процессы и подписи;
- `restart(target_id)` — перезапуск одного;
- `restart_all()` — последовательный перезапуск всех;
- `get_status(operation_id)` — результат операции.

Если порт не передан, раздел рестарта не показывается. Кузов или серверный
адаптер задаёт реальные команды и права. Управляющий процесс при `restart_all`
перезапускается последним.

Рама отвечает за:

- права суперадминистратора;
- выбор цели;
- двойное подтверждение;
- защиту от повторного клика;
- аудит запроса и результата;
- понятный экран ошибки.

Серверный адаптер отвечает за настоящий рестарт и проверку нового процесса.

### 5.2 Политики фоновых задач

Чтобы не раздувать `BotChassisConfig`, добавить два компактных объекта:

- `BackupPolicy | None`;
- `ReportingPolicy | None`.

Они передаются в конец keyword-only параметров фабрики. `None` полностью
отключает соответствующую автоматику и сохраняет поведение `0.2.2`.

`BackupPolicy` содержит только универсальные параметры: каталог, часовой пояс,
время, число daily/weekly-копий. `ReportingPolicy` — время и направления
системных отчётов. Доменных настроек внутри нет.

Планировщик не стартует при импорте библиотеки. Фабрика регистрирует его на
`Dispatcher.startup`, а на `Dispatcher.shutdown` отменяет и дожидается фоновой
asyncio-задачи. `scheduler_owner_origin_bot_id` внутри политики необязателен:
если задан, только этот процесс поднимает цикл; если не задан, процессы
соревнуются за уникальный DB-claim. Рекомендуемый сетевой режим — назначенный
owner, у чьего Telegram-бота проверены права в events/ops-темах; DB-claim всё
равно остаётся страховкой от дубля.

### 5.3 Точки подключения кузова

Все точки передаются keyword-only в конец фабрики, имеют безопасный `None` и
не попадают в `BotChassisConfig`, если являются поведением, а не данными:

- `render_start_callback(context)` — единый стартовый экран кузова и возврат
  «Назад» из поддержки;
- `decorate_info_markup(markup, context)` — добавляет рамный языковой ряд к
  готовой Info-карточке кузова без второго Info-хука и второго сообщения;
- `on_locale_changed(context)` — перерисовывает текущий кузовной экран после
  смены языка;
- `bot_display_name_provider(origin_bot_id, telegram_bot_id)` — подписи ботов
  в досье и событиях без BPD/ADHD в коде рамы;
- `initial_locale_resolver(language_code)` либо декларативная
  `InitialLocalePolicy` — настраиваемая RU-группа и fallback EN;
- `review_sink` — модерация, публикация и возврат ссылки на отзыв;
- `process_control` — реализация `ProcessControlPort`;
- `donation_catalog` — внешний список донатных SKU; при `None` используются
  только переданные `SkuItem(issues_voucher=False)`, пустой список скрывает
  кнопку поддержки проекта.

Для Info меняется контракт callback: кузов возвращает описание карточки
(`text/media/markup/policy`) либо использует предоставленный renderer рамы, а
не самостоятельно отправляет непрозрачный `Message`. На переходный период
старый `render_info_callback -> Message` поддерживается, но языковой ряд в его
готовую клавиатуру рама не вставляет и пишет диагностическое предупреждение.

### 5.4 Разделённые ожидания ввода

Один словарь `PendingInputStore[user_id]` больше не используется сразу всеми
контурами. Ввод разделяется минимум на scopes:

- `user_navigation`: новое обращение, ответ в существующий тикет, отзыв;
- `admin_navigation`: поиск пользователя и другие формы админки;
- `broadcast`: собственная сессия рассылки;
- `domain`: остаётся во владении кузова.

`PendingInput` получает `ticket_id` и отдельные kind для нового тикета,
продолжения тикета и отзыва. Администратор, который одновременно является
пользователем поддержки, не стирает ожидание собственного админского поиска.

### 5.5 Контракт хранилища поддержки

- `SqliteSupportThreadStore` — обязательный backend для `in_progress`, reopen,
  истории метаданных и сети из нескольких процессов.
- Старый JSON `SupportThreadStore` сохраняется как совместимый одноразовый
  режим `0.2.2`: первый ответ закрывает/освобождает обращение, продолжение и
  reopen недоступны.
- При постоянном `db_path` и отсутствии явно переданного store фабрика `0.3`
  создаёт SQLite-store с `tenant bot_id`, `resolved_origin(config)` и
  фактическим `bot.id` без сетевого запроса. Для `:memory:` и явного legacy-
  store действует одноразовый режим.
- `/support` остаётся скрытым совместимым shortcut и сразу включает ввод нового
  обращения. Кнопка нижнего меню «Поддержка» открывает новый обзорный экран;
  поэтому замороженный сценарий команды остаётся зелёным.

11. `feat(backup): schedule verified rotating snapshots`
12. `feat(reports): send chassis operational summaries`
13. `feat(admin): add role-aware floating control panel`
14. `feat(ops): add process control port`
15. `docs: publish chassis 0.3 canon`
16. отдельный инфраструктурный шаг переименования.

Если один гейт оказывается слишком большим, его сначала делят в плане на
самостоятельные проверяемые части. Несвязанные изменения в коммит не добавлять.

## 8. Финальные инварианты

- Старый вызов фабрики без новых аргументов работает как в `0.2.2`.
- Новые параметры фабрики — keyword-only, в конце, с дефолтом `None`.
- `bot_gateway.py` не ломать.
- Деньги и платежный гейт не смешивать с lifecycle.
- `bot_id` остаётся tenant-ключом; фактический Telegram bot ID не заменяет его.
- Рама не знает бизнес-логику и конкретные процессы кузова.
- Секреты и настоящий `.env` не читать и не коммитить.
- Live Telegram smoke, системные рестарты, push и переименование — только по
  отдельному подтверждению владельца.
- Каждая миграция SQLite проверяется на новой и существующей базе.
- Автоматические задачи одной общей базы исполняются только одним процессом.

## 9. Рабочие промпты и границы контроля

- `.agents/IMPLEMENTATION_0_3_PROMPT.md` — coding-чат, строго один гейт за
  запуск, после сдачи останавливается.
- `.agents/AUDIT_0_3_PROMPT.md` — независимый read-only аудит конкретной
  границы, без исправления кода.
- Внутренняя проверка обязательна после каждого гейта.
- Независимые аудиты: B0 после Gate 0; B1 после Gate 1A; B2 после Gate 3; B3
  после Gate 5C; B4 после Gate 8; B5 после Gate 10; B6 после Gate 12.
- Любая стоп-линия из промптов вызывает внеплановый аудит до продолжения.
