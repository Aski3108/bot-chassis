# Промпт узкой реализации Bot Chassis 0.3

Скопируй текст ниже в coding-чат. На один запуск указывай ровно один гейт.

---

Ты — исполнитель одного узкого этапа релиза **Bot Chassis 0.3 — Operational
Upgrade**. Не реализуй весь план подряд.

Рабочий корень: `C:\Python\bot_chassis`.

Текущая задача:

- `TARGET_GATE={{ровно один: Gate 0, Gate 1, Gate 1A, Gate 2 ... Gate 12}}`
- `ACCEPTED_BASE={{принятый коммит или HEAD предыдущего этапа}}`
- `AUDIT_BOUNDARY_AFTER={{B0–B6 либо none}}`

Если `TARGET_GATE` не указан или содержит несколько гейтов, не начинай код:
попроси владельца назвать один этап.

## Обязательный вход

Перед любым изменением полностью прочитай:

1. `.agents/AGENTS.md`
2. `.agents/NEW_CHAT.md`
3. `.agents/SESSION_STATE.md`
4. `.agents/PROJECT_CONTEXT.md`
5. `.agents/ACTIVE_PLANS.md`
6. `.agents/TASK_TODO.md`
7. весь `.agents/UPGRADE_0_3_PLAN.md`
8. релевантные разделы `docs/CHASSIS.md`

Затем найди в плане только `TARGET_GATE`, его входные контракты и проверки.
Сначала кратко сообщи владельцу: что меняешь, что намеренно не меняешь и
какими тестами докажешь результат.

## Жёсткие границы работы

- Реализуй только `TARGET_GATE`. Не начинай следующий гейт автоматически.
- Не добавляй «полезные заодно» рефакторинги и исправления.
- Не открывай и не меняй PsyBot, Chat Listener и Profiling Framework.
- Не читай `.env`, токены, DSN и секреты.
- Не делай push, переименование репозитория, live Telegram smoke и реальный
  restart без отдельной прямой команды владельца.
- Не двигай tag `profiling`.
- Не меняй `bot_gateway.py` и публичные контракты вне явно разрешённого пункта.
- Новые параметры фабрики: только keyword-only, в конце, с дефолтом `None`.
- Старый вызов фабрики без новых аргументов обязан работать как раньше.
- Не тащи в раму опросники, `/detect`, названия BPD/ADHD, серверные unit-имена,
  LLM и другую логику кузова.
- Сохраняй чужие изменения грязного worktree. Если они пересекаются с твоими
  файлами и безопасно разделить нельзя — остановись и сообщи владельцу.

## Frozen-контракт

`tests/test_chassis.py` заморожен, кроме трёх заранее разрешённых изменений в
Gate 1:

1. `test_main_menu_keyboard_toggles_and_domain_rows`;
2. `test_register_button_chassis_startup_hook`;
3. `test_setup_bot_commands_merges_custom_commands`.

В любом другом гейте файл не менять. Остальные 16 тестов не переписывать под
новую реализацию и не ослаблять.

## Рабочий цикл одного гейта

1. Проверь `ACCEPTED_BASE`, статус Git и отсутствие незаконченного предыдущего
   этапа.
2. Выпиши критерии готовности текущего гейта из плана.
3. Назови точный список предполагаемых файлов. Если для выполнения требуется
   выйти за контракт гейта, остановись и сначала предложи правку плана.
4. Добавь/обнови узкие тесты, которые падают без нужного поведения.
5. Реализуй минимальный код текущего гейта.
6. Прогони узкие тесты контура.
7. Прогони полный `pytest tests -q`, если план гейта не разрешает более узкую
   остановку. Нельзя сдавать этап с известным красным тестом.
8. Проверь `git diff --check`, публичные сигнатуры, миграцию и посторонний diff.
9. Обнови `SESSION_STATE`; другие журналы меняй только когда этого требует
   контрольный план и этап действительно принят.
10. Не создавай коммит без явного разрешения владельца. Если разрешение дано —
    один гейт = один осмысленный коммит.
11. Сдай отчёт и остановись. Следующий гейт не начинать.

## Когда обязателен аудит

Внутренняя самопроверка выполняется после каждого гейта. Отдельный чат-аудитор
обязателен на следующих границах:

- `B0`: после Gate 0;
- `B1`: после Gate 1A;
- `B2`: после Gate 3;
- `B3`: после Gate 5C;
- `B4`: после Gate 8;
- `B5`: после Gate 10;
- `B6`: после Gate 12.

Если текущий гейт заканчивает такую границу:

1. Не переходи дальше.
2. Подготовь `BASE_REF`, `HEAD_REF`, список изменённых файлов и команды тестов.
3. Предложи владельцу запустить `.agents/AUDIT_0_3_PROMPT.md` в отдельном чате.
4. Следующий этап разрешён только после `PASS` или принятого владельцем
   `PASS WITH NOTES`.

## Немедленная внеплановая остановка

Остановись до продолжения, если:

- план и текущий код требуют несовместимых решений;
- нужна новая таблица/колонка/публичный порт, не описанные в гейте;
- требуется изменить дополнительный frozen-тест;
- обнаружен риск потери данных, утечки tenant или обхода root/staff;
- миграция не может быть повторяемой;
- для успеха нужен код соседнего репозитория;
- тест падает по причине, которую нельзя исправить внутри текущего гейта;
- рабочие изменения владельца пересекаются с твоим diff.

Не маскируй такую ситуацию временной заглушкой. Дай короткий факт, риск и
минимальное решение, после чего жди решения владельца.

## Формат сдачи одного гейта

Ответь коротким списком:

1. Итог человеческим языком.
2. Какие файлы изменены.
3. Какие проверки запущены и их результат.
4. Что намеренно осталось за пределами этого гейта.
5. Нужен ли сейчас независимый аудит и какая это граница.
6. Коммит создан или нет; push всегда отдельно.

Не пиши «всё готово», если хотя бы один критерий гейта не доказан.
