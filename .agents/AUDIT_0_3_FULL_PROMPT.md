Этот промпт предназначен для **нового независимого чата-аудитора**. Он не
заменяет `.agents/AUDIT_0_3_PROMPT.md`: общий промпт остаётся шаблоном для

диапазон `v0.2.2 → 0.3.1`, используя этот чек-лист для части `0.3.0` и
`.agents/AUDIT_0_3_1_PROMPT.md` для части `0.3.1`. До завершения Gate R1

## 7. Подробная проверка по гейтам

### Gate 0 — control plane и исходная точка

- Один технический план, одна живая очередь, один project log.
- Bootstrap-порядок согласован во всех правилах.
- Baseline `0.2.2` воспроизводим и отделён от `0.3.0`.
- Нет второго исполняемого плана в архивных документах.

### Gate 1 — меню, единый Start и Info

- Все включённые служебные кнопки в одном ряду; старые подписи — только
  входные алиасы.
- Системное меню содержит `/menu` плюс разрешённые команды кузова; скрытые
  `/start`, `/help`, `/support` продолжают работать.
- Рама — единственный владелец `Command("start")`; второй доменный handler
  выявляется до запуска.
- Один `/start` создаёт ровно один носитель Reply-клавиатуры и не более одной
  стартовой карточки кузова.
- Один Info-клик не создаёт двойного ответа.
- В `tests/test_chassis.py` изменены только три разрешённых сценария Gate 1;
  остальные 16 сравни с `BASE_REF` поблочно.
- `src/bot_chassis/bot_gateway.py` не изменён.

### Gate 1A — локаль

- Один toggle `ru ↔ en`, точные динамические подписи.
- Вся RU-группа и региональные коды; неизвестный/пустой код → EN.
- `auto/manual/legacy` мигрируются без перезаписи ручного выбора.
- Смена языка не сбрасывает pending/domain state и текущий шаг.
- Start/Info и callback кузова перерисовываются без двойных сообщений.
- Старый callback совместим и не мутируется небезопасно.

### Gate 2 — Telegram topics

- Все thread ID опциональны и не ломают старый конфиг.
- При `None` аргумент `message_thread_id` не отправляется.
- Fallback-чат никогда не получает thread ID другого чата.
- Reply поддержки сверяется с исходным chat/thread, а не только с текущим
  конфигом.
- Ошибки, оплаты, аудит, ops, events и support идут в правильные направления.

### Gate 3 — per-bot lifecycle

- Tenant-санкции не смешаны со статусом фактического Telegram-бота.
- Ключ и запросы содержат правильные `bot_id`, `origin_bot_id`,
  `telegram_bot_id`.
- `my_chat_member` не троттлится и входит в канонический `allowed_updates`.
- Первый `/start` имеет отдельный атомарный claim и одно событие.
- Временная доставка не портит статус; blocked/deactivated классифицируются
  правильно.
- `deleted` не утекает между tenant.

### Gate 4 — поиск и команды

- ID/username, `@`, регистр, отсутствие и дубликаты старых данных.
- Username очищается при `None`; новый владелец освобождает старое значение
  только внутри tenant.
- Все перечисленные админ-команды используют один resolver.
- Pending поиска изолирован минимум по `(bot_id, actor_id)` и не конфликтует
  с поддержкой/рассылкой/доменом.

### Gate 5A — поддержка и донаты

- Обзор → запрос/отзыв/донат → назад; скрытая `/support` совместима.
- Рама не содержит доменные суммы; внешний каталог согласован с invoice,
  pre-checkout и записью платежа.
- Пустой каталог/отсутствующий sink скрывает действие безопасно.
- Pending scopes не стирают друг друга.

### Gate 5B — продолжаемый SQLite-тикет

- `open → in_progress → closed`, явный reopen, первый ответ не закрывает.
- Пять активных тикетов ограничивают только новый шестой, не продолжение.
- Метаданные сообщений без текста/медиа.
- Чужой bot/chat/thread не может доставить ответ.
- Постоянный SQLite-store выбирается автоматически; `:memory:` и явный JSON
  остаются одноразовым legacy без dual-write.
- Миграция `answered → closed` безопасна и повторяема.

### Gate 5C — отзывы

- Текст/одно медиа/подпись, явное согласие, без хранения содержимого.
- DB-строка создаётся до внешней копии; ошибка компенсируется и разрешает
  повтор.
- Publish/reject защищены атомарным claim; второй publish не проходит.
- Протухший moderation claim восстанавливается; старый token не завершает
  новый claim.
- Только superadmin модерирует; после публикации пользователь получает ссылку.

### Gate 6 — XLSX

- Все пользовательские таблицы обнаруживаются динамически; `sqlite_*`
  исключены; неизвестная таблица не исчезает.
- Tenant-фильтр применяется только к таблицам с `bot_id`; global явно отмечен.
- `_manifest`, физические колонки, вычисляемые представления, ссылки,
  автофильтр, freeze panes, даты и formula-injection проверены.
- Временные файлы удаляются на ошибке и после отправки по контракту caller.
- Критический Low B4: `build_xlsx_export` сначала делает
  `StorageEngine.backup`, затем строит книгу из отдельного snapshot в thread;
  тяжёлая сборка не идёт через `engine.run` и не держит `BEGIN IMMEDIATE`.
- Проведи независимый тест: намеренно задержи стадию записи workbook и докажи,
  что параллельная запись в живую SQLite завершается до освобождения задержки.

### Gate 7 — backup и scheduler claim

- Снимок делается через SQLite backup, проходит `integrity_check`, ZIP содержит
  ровно один `.db`, публикация файла атомарна.
- Общий deadline ограничивает один зависший backup, retry/backoff не выходит
  за него.
- Ротация 14 daily / 8 weekly, воскресенье — rename без второй копии; при
  ошибке старые архивы не удаляются.
- Ручной `.db`: лимит транспорта и правила сохранения/удаления соблюдены.
- Семь процессов дают одного победителя на свежем слоте.
- Критический Low B4: `claimed/running` старше
  `claim_stale_after_seconds` атомарно перехватывается; `done/failed` никогда
  не перехватываются; после гонки семи процессов победитель один.
- У каждого экземпляра scheduler уникальный внутренний claim-owner. После
  перехвата старый владелец не может записать `running/done/failed`.
- Проверь обе политики — backup и report — и совместимость старого вызова
  repository без stale-параметра (`ON CONFLICT DO NOTHING`).
- Оцени остаточный риск lease: долгий живой исполнитель после истечения stale
  не должен давать неописанные двойные внешние эффекты. Если гарантия только
  recovery после реально умершего процесса, документация должна говорить
  именно это; не приписывай коду exactly-once без доказательства.

### Gate 8 — отчёты

- Первый запуск до 23:30 не берёт вчерашний слот.
- Период начинается после последнего `done`; failed не создаёт дыру.
- Первый период ограничен локальной полуночью или `reporting_started_at`.
- Sunday/month-end границы UTC+5 независимы и не удваивают daily.
- Метрики только рамы; ошибки берутся из неизменяемых `chassis_events`.
- Доставка events/ошибка ops; tenant и donation SKU не смешаны.
- Повторный запуск и семь процессов не дают обычного дубля отчёта.

### Gate 9 — админка

- Staff/root проверяются и в отображении, и на callback/command.
- Staff не видит и не вызывает рассылку, Excel, backup, restart, роли, подарки.
- Extra home rows не обходят root-only меню.
- Одна активная панель: переход редактирует, значимый результат остаётся,
  старая панель теряет кнопки, новая поднимается вниз.
- Поиск и `/user` также снимают старую панель.
- Preview/confirm нельзя повторно нажать; итог рассылки чистый.

### Gate 10 — process control

- Универсальная рама не содержит shell/systemd/Docker и имён процессов.
- Без порта раздел отсутствует; restart только root.
- Одноразовый token, блокировка параллельной цели, последовательный «все»,
  управляющий последним.
- Успешно доставленный аудит обязателен **до** первого вызова порта; отсутствие
  destination или ошибка доставки отменяет restart.
- Ошибка `get_status` одной цели не рвёт остальные и финальный отчёт.
- Рама вызывает последовательные `restart()`, а `restart_all()` остаётся
  контрактом адаптера/тестов согласно позднему решению.

### Gate 11 — окружение и документы

- В Git нет настоящего `.env` и секретов.
- `.env.example` содержит только параметры рамы, без доменных брокеров.
- `AUDIT_CHAT_ID` остаётся каноническим; нет дублирующего
  `SUPERADMIN_CHAT_ID`.
- Документированы thread IDs, политики, `/start`, Info, SQLite support и
  `my_chat_member`.
- README, пример запуска, канон и фактические сигнатуры согласованы.

### Gate 12 — интеграция и release readiness

- Версия `0.3.0` едина в package metadata, changelog, version log и каноне.
- Старый вызов фабрики без новых аргументов работает.
- Все новые фабричные параметры keyword-only, добавлены в конец и имеют
  безопасный `None`/дефолт.
- Contract-тест доказывает один Start, один Info, locale без сброса,
  `my_chat_member`, внешний donation catalog, single bot и сеть семи origin.
- Gate 13 действительно не нужен для выпуска и нигде не заявлен выполненным.
- `v0.3.0` не создан до отдельной команды владельца.

## 9. Безопасность, приватность и конкурентность

Сделай отдельный review:

- SQL parameters и динамические identifiers;
- Excel formula injection и утечки чужого tenant/global tables;
- права staff/root и прямые поддельные callback;
- payment identity: tenant, provider, merchant Telegram bot ID, payment ID;
- отсутствие текстов тикетов/отзывов в SQLite;
- отсутствие секретов и внутренних traceback у пользователя;
- атомарные claims reviews/jobs/first-launch;
- гонки семи SQLite connections;
- повторные клики, повторная доставка, crash между claim и final status;
- cleanup временных `.db/.xlsx/.zip` на каждом исключении;
- cancellation startup/shutdown scheduler без фоновых «зомби»;
- отсутствие реальной системной команды restart в универсальном пакете.

Для каждой конкурентной гарантии ищи не только `Lock`, но границу между
SQLite-транзакцией и внешним побочным эффектом Telegram/filesystem.

```text
git diff --check BASE_REF..HEAD_REF
```

Дополнительно запусти узкие наборы Gate 1–5 и Gate 9–12, если полный вывод не
позволяет доказать их отдельно. Не подменяй полный прогон суммой выборочных.

Обязательные ad-hoc проверки во временном каталоге, без правок репозитория:

1. Замедленная сборка XLSX + успешная параллельная запись в live DB.
2. Семь конкурентных stale-claim на один старый `running` слот: один winner.
3. Старый owner не завершает перехваченный слот.
4. `done` и `failed` не перехватываются даже при древнем `started_at`.
5. Семь обычных процессов дают один backup/report claim.
6. Миграция `0.2.2 → 0.3.0 → повторная initialize` с данными.
7. Старый вызов фабрики без новых аргументов.

Если тест нельзя запустить, укажи точную команду, причину и какое утверждение
остаётся недоказанным. Не заменяй пропущенную проверку фразой «по коду всё
нормально».

Ориентиры прошлых прогонов (`218 full`, `19 frozen`, `20 Gate 6–8`) — только
сигнал расхождения. Не требуй именно эти числа, если новые versioned тесты
обоснованно изменили счётчик; объясни любую разницу.

## 11. Немедленная стоп-линия (`BLOCKED`)

Ставь `BLOCKED`, если найдено хотя бы одно:

- failing test или скрытый skip/xfail критического контракта;
- изменение frozen-теста вне трёх разрешённых сценариев Gate 1;
- изменение/поломка `bot_gateway.py`;
- несовместимый старый вызов фабрики или позиционного публичного API;
- второй `/start`, Info, payment, ticket publish или scheduler execution;
- tenant/origin/Telegram bot ID перепутаны;
- обход root/staff;
- потеря данных, неидемпотентная миграция, REAL для денег;
- секрет/настоящий `.env`/пользовательская база в Git;
- доменная логика кузова в раме;
- реальная системная команда restart;
- ночной backup не восстанавливается либо ротация может удалить старые копии
  после ошибки нового снимка;
- stale claim нельзя восстановить после crash либо несколько претендентов
  одновременно считают себя победителями;
- XLSX снова строится под `BEGIN IMMEDIATE` или допускает утечку tenant;
- docs объявляют гарантию, которой код не даёт;
- проверяемый HEAD не соответствует заявленному срезу.

## 12. Шкала находок

- **Blocker** — выпуск нельзя продолжать: данные, деньги, права, секреты,
  совместимость, дубли внешних действий, миграция или ключевой контракт.
- **High** — реалистичный серьёзный эксплуатационный сбой; до релиза исправить.
- **Medium** — контракт частично нарушен или важный сценарий не доказан.
- **Low** — ограниченный риск/недостающая защита без нарушения основного пути.
- **Note** — трассировка, документация или улучшение доказательств без дефекта
  поведения.

Не понижай приоритет только потому, что предыдущий аудит пропустил проблему.
Не повышай косметику до blocker.

## 13. Формат итогового ответа

Первая строка — только один вердикт:

- `PASS`
- `PASS WITH NOTES`
- `BLOCKED`

Далее обязательно:

1. **Проверенный срез** — refs, ветка, чистота WORKTREE, commits, diff-stat.
2. **Находки** — таблица, сначала Blocker/High:

   | ID | Приоритет | Файл:строка | Требование | Факт и доказательство | Риск | Точное исправление | Нужная регрессия |

   Если дефектов нет, напиши «дефектов не найдено», но Note о гранулярности
   landing-коммита оставь отдельно.
3. **Матрица Gate 0–12** — для каждого Gate: доказано / частично / нет,
   ключевые файлы и тесты.
4. **Повтор прежних находок B0–B6** — каждая закрыта или снова открыта.
5. **Два Low B4** — отдельный подробный вывод по Excel snapshot и stale claim.
6. **Миграции и данные** — что реально запускалось и что сохранилось.
7. **Совместимость API/frozen** — фабрика, dataclasses, `bot_gateway.py`,
   `tests/test_chassis.py`.
8. **Безопасность и конкурентность** — tenant, права, claims, внешние эффекты,
   секреты.
9. **Тесты** — команды, точные результаты, duration, skips/warnings/failures.
10. **Документы и release readiness** — версия, changelog, canon, examples,
    tag state, Gate 13.
11. **Посторонний diff** — перечислить либо явно написать, что его нет.
12. **Непроверенное** — любые ограничения аудита; пустой раздел запрещён,
    если что-то не запускалось.
13. **Команда завершения**:
    - для `PASS`: «0.3.0 готов к следующему отдельно разрешённому релизному
      действию»;
    - для `PASS WITH NOTES`: что можно делать и какие notes остаются;
    - для `BLOCKED`: «сначала исправить перечисленные Blocker/High и повторить
      полный аудит на новом HEAD_REF».

Не редактируй журналы сам. Верни доказательный отчёт владельцу; отдельный
coding/control-plane чат запишет принятый вердикт после решения владельца.
